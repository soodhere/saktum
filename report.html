State of MCP Trust

How ready are the MCP servers that AI agents depend on? We examined the 2,404 most-relevant MCP server packages on npm, covering 5,167,675 weekly downloads, and ran Saktum Check on the 1,020 most-used servers. Here’s what we found, and what maintainers can fix this week.

Since November

The scope grew, so the headline numbers are not a trend. November assessed the 103 most-used npm servers; December assessed 540 servers (including 26 Python servers) and 381 remote servers, many of them less used. Shares such as the 35% without danger annotations (48% in November) describe different sets of servers.

Like for like: 36 servers were assessed in both months. Of these, 35 kept their level, 1 improved and 0 fell; 14 are agent-ready and 7 reach L5 in both months. One month, before outreach to maintainers, is too short to expect change; the January census will show whether fixes spread.

Rigour note: review before publication found two secret-detection false positives (a parameter description mentioning "password:" and AWS's documented example key in a usage example). Both servers are clean; the detector was corrected in Saktum Check 0.4.1 and the figures here reflect the correction.

What we found

Agent readiness

35% of servers declare no danger annotations and 5.6% declare them on only some tools. 52.4% earn agent readiness A. Tool definitions cost a median of 5,047 tokens per agent turn (90th percentile 32,833), and 87 servers exceed 20,000 tokens before an agent does any work.

Five fixes for maintainers

  1. Declare danger annotations (readOnlyHint, destructiveHint) on every tool, so clients can ask before an agent deletes something.
  2. Trim tool definitions: every token is paid on every agent turn. Shorten descriptions and drop rarely used tools.
  3. Publish with npm provenance (npm publish --provenance from CI) and avoid install scripts.
  4. Answer unknown tools with an error, never success, and keep errors free of stack traces and file paths.
  5. Test what your tools return: declare an outputSchema and run your own test cases in CI (npx saktum test).

Method, ethics and limits

Supply-chain signals come from public npm registry metadata. The deep assessment installed each server with install scripts disabled and ran Saktum Check Saktum Check 0.4.0 in passive mode on a disposable machine: no tool was called, no credentials were supplied, and nothing was sent to any third-party service. Servers that need configuration to start (473 of 1,020) or that list no tools without credentials (7) are not graded. This report names no server; individual results are shared only with maintainers on request. Results describe each package at the time of the census and are not a guarantee of security. Capability inference is deliberately conservative and may miss capabilities rather than invent them.
