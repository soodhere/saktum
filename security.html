Trust centre

Security of Saktum itself

A trust product has to be trustworthy itself. Here is exactly how Saktum handles your environment and evidence.

Runs in your environment

Saktum Check runs on your machines and CI. There is no Saktum service in the path and no customer data sent to us.

Passive by default

Checks never call a server's tools unless you choose to, for servers you own.

Secrets stay yours

Secrets are never printed; receipts keep digests of arguments, not values; headers are never logged.

Signed, verifiable evidence

Ed25519 signatures on results, mandates, approvals, agreements and receipts; receipts are hash-chained, so changes and removals are detected.

Protected keys

Keys from your OS keychain (macOS Keychain, Linux Secret Service, Windows DPAPI), an environment variable, or any cloud key service or hardware module through an external signer. The private key never needs to enter Saktum.

Supply chain

Open source; npm provenance; a CycloneDX SBOM with every release; dependencies audited in CI.

Built to resist its own compromise

The stop button sticks

Revocations are signed, recorded in the append-only receipt chain, and can come from a remote list the agent cannot edit.

Deletions are detectable

Signed checkpoints of receipt logs and the ledger catch removed or rewritten entries; independent witnesses can countersign the ledger.

Approvals you can trust

One exact action, once, by a per-request link, optionally confirmed with a passkey (Face ID, Touch ID, Windows Hello or a security key).

No silent changes

Proxies pin a server's exact tools and refuse calls if they change; any error refuses the call (fail-closed).

Verified organisations

Organisations prove control of their domain by DNS or a well-known file, re-checkable by anyone.

Private by design

Receipts keep keyed digests of arguments, so even guessable values cannot be recovered.

Verify Saktum itself

npm audit signatures checks npm provenance. Every release ships a SHA-256 checksum, an SBOM and a Sigstore signature; npx saktum self-verify compares your copy. Our workflows pin every action to an exact commit, and CodeQL, Dependabot and the OpenSSF Scorecard run on the code. To verify a passport, receipt or attestation yourself, use Verify it yourself: it runs in your browser and uploads nothing.

Security roadmap

Next: an independent security review and penetration test, then SOC 2 Type I before enterprise general availability of the hosted gateway, and a bug bounty for Saktum itself. Full detail: the threat model, security architecture and hardening guide in the repository.

Data flow

Agent → saktum proxy on your machine (decides against the mandate, agreement, approvals and revocations) → only allowed calls reach the MCP server → a signed receipt is written to your folder. Optional, and only if you configure them: your OpenTelemetry collector and your approval webhook.

Honest limits

Saktum governs MCP tool calls, not raw shell commands: use it with a sandbox for agents with shell access. It contains a manipulated agent through its mandate but does not detect prompt injection inside models. No external penetration test or certification yet (planned after funding); the code is open for your own review.

Report a vulnerability

Use GitHub's private vulnerability reporting on the repository. We acknowledge within 3 business days and coordinate disclosure within 90 days.
